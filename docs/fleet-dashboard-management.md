# Infrastructure dashboard

Hosts collects Fleet observations into SQL every 15 seconds, independently of open browsers. History offers hour (default), eight-hour, day, week, month and custom ranges up to 32 days. Raw observations remain stored; chart queries select the latest real observation per interval (about 900 points), without permanent downsampling or fabricated gap values. Collection starts when this version is deployed; old samples are not reconstructed. There is no retention policy yet.

The comparison viewer uses a compact sidebar with multiple selected measures and hosts grouped by detected NVIDIA GPU family. Hosts sort naturally by name. Measures with the same unit share an axis; different units get separate aligned plots, with stable host colors and metric line styles. Metrics include CPU/system memory, network RX/TX, GPU utilization/dedicated memory, SM/memory clocks and temperature. GB10 unified memory stays system RAM; unavailable dedicated VRAM remains blank. Clicking a host opens its history and latest device, network, model and container details.

Recipes lists executable revisions separately from the retained import/archive bank. Compose and Sparkrun **are importable**: preview conversion, resolve required inputs, save an immutable portable Fleet revision and then place it through Deployment. JSON editing uses locally bundled Monaco with JSON diagnostics/formatting. Existing revisions stay immutable. Archived entries are excluded from executable/deployment selectors.

## Importing Local Inference Lab builds

On Recipes, choose **Import LiL URL** and paste a configuration link from
`https://docker.local-inference-lab.ai/?build=…&model=…`. **Load LiL recipe**
downloads that configuration's Compose YAML, preserving its selected build,
model, preset and overrides. The controller fetches only the fixed HTTPS origin's
`/compose.yaml`, without redirects, with a 15-second timeout and a 32 KiB limit;
the operation requires administrator and CSRF authorization. It does not start a
container or save a revision.

Review the YAML, supply a container user and RAM admission limit, and map named
cache volumes to approved absolute host paths. Conversion preserves the pinned
image, profile launcher, GPU count, environment and command. Optional bare
`HF_TOKEN` passthrough is omitted when no private host environment file is selected;
explicit credential references require such a file. Controller credentials are
never inherited. Review host-network/ports, cache ownership and security options
against the chosen host's Fleet policy. Named-volume mapping does not migrate
existing Docker volumes. Save the source and executable revision, then deploy
through the ordinary host/GPU placement controls.

Converted recipes retain `metadata.source_url`, linking the catalog back to the
original configuration. RTX PRO hardware applicability is inferred only when the
LiL launch explicitly selects `rtx-pro-6000-pcie`. RAM limits and exclusive GPU
ownership are admission envelopes, not automatically measured minimums. Imported
recipes begin untested; startup, smoke, memory and benchmark evidence remain
specific to the pinned executable configuration and hardware.

`POST /dashboard/api/management/recipes/source` accepts `{"url": "…"}` and
returns source URL, Compose content, suggested recipe ID and named-volume names.
Conversion options additionally accept `source_url` and
`volume_paths: {"volume-name": "/approved/host/path"}`. A missing mapping blocks
conversion; relative mappings and credentials are rejected.

Distributed revisions contain `distributed: [rank0_spec, rank1_spec, ...]` (two to eight ranks). Addresses live in deployment placement, substituted for `{{head_address}}`, `{{host_address}}`, `{{node_rank}}` and `{{num_nodes}}`. Select ordered hosts and reachable fabric addresses; rank zero is the head. Preserve NCCL environment and choose a compatible fabric. DAC-only recipes require partner Sparks. The central selection commits all desired ranks atomically; local starts remain asynchronous, with partial failure visible per rank. Single-host recipes may also be placed as independent replicas on several hosts. IDs are generated by the server. Whole groups start/stop through the same selection API and expected generations.

`POST /dashboard/api/management/adopt` supports catalog cleanup of existing placements: map deployment IDs to existing revisions, expected generations and optional placement, and optionally archive old recipe IDs. Every old and new rendered runtime specification must match exactly; the whole update fails atomically on differences/conflicts. Generations advance, allowing Fleet to adopt identical execution without restarting containers. Execution changes require normal unload/select/start.

Startup readiness, operator smoke validation (at least two requests) and benchmark evidence are stored in SQL against exact revision digest, host and deployment generation. Startup is distinguished from inference validation. Benchmark evidence retains options, image/tool provenance and bounded result cells even after the live run catalog rotates. A changed executable configuration begins untested. Metadata-only revisions show evidence for the identical executable configuration, retaining links to the original measurements. The catalog reports measurements for recorded hardware, not universal performance claims.

Models groups by served model with every host as a sub-row. Gateway request activity uses SQL and the existing 1m/15m/1h/4h/24h windows. Direct calls and heartbeats are excluded; per-rank counts remain blank where attribution is unavailable. All infrastructure/Traffic tables reuse the shared component for column filtering, numeric sorting, visibility and responsive details. Benchmarks retains the live result matrix and adds per-user/aggregate decode throughput to the detailed measurement table.

Portable recipe annotations live in optional `model_spec.metadata`: `gpu_families` identifies supported detected families (`spark`, `rtx-pro-6000-blackwell`, or an exact GPU name), `image_sources` maps each pinned image identity to its readable repository/tag, and `image_source_urls` maps it to a credential-free HTTP(S) registry or build source. Annotations are validated, included in the immutable revision digest and removed before sending the executable specification to Fleet. Distributed recipes can carry annotations alongside `distributed`. Empty/absent hardware applicability remains unspecified; it does not assert universal compatibility. GPU counts derive from explicit `device=...` selections and sum across ranks; `all` stays unspecified rather than guessing.

The catalog exposes Copy and New JSON recipe actions, readable image provenance, C1/C4/C16 decode at exactly 8,192 context tokens (total/per-user tok/s from the same cell) and best measured prefill with its context depth. Best decode excludes errors, skipped/failed and capacity-limited cells. Links retain run/host provenance; absent measurements stay blank. Prefill reports fresh-prompt throughput, separately from decode and with full-request TTFT.

Deployment host selection appears after choosing a recipe. Hosts sort by name, filter by detected compatible GPU family and show unreserved GPU counts plus measured free dedicated VRAM; Sparks show available unified system RAM. Stale observations cannot authorize a new placement. Hardware-declared recipes are also checked against live detected GPU names by the single/group selection API. Unload operations remain available regardless of hardware observations. Capacity is advisory; Fleet remains responsible for reservations and execution. Model and deployment placement columns show linked short host names.

Benchmark concurrency and context matrices use preset chips and bounded custom numeric values. The recipe-comparison preset measures C1/C4/C16 at 8k/32k. Prefill has a prominent, context-sorted result table that includes planned depths before results arrive and preserves pending, skipped, disabled and unmeasured states. Zero context does not fabricate a prefill measurement.

## Named recipe sizes and memory admission

Executable recipes can contain up to 16 `sizes`, keyed by a lowercase name. A size
contains `description`, `overrides` (executable settings such as RAM, environment
and GPU reservations) and `vllm` (typed overrides for GPU utilization, KV bytes,
model length, sequence count and batched tokens). Overrides must match an existing
literal command flag or recognized environment setting; arbitrary shell values
are rejected. Environment patches retain unrelated variables. Example:

```json
{
  "sizes": {
    "shared": {
      "description": "Share a Spark with other small services",
      "overrides": {
        "memory_limit": "40g",
        "gpu_memory": {"mode": "shared", "mib_per_device": 32768}
      },
      "vllm": {"gpu_memory_utilization": 0.3, "kv_cache_memory_bytes": "8G"}
    }
  }
}
```

Use Add size in the recipe editor, then edit its JSON; Deployment offers a size
selector and previews each host's budget and the requested estimate. Selecting a
size materializes a distinct immutable revision, deduplicated by digest and
annotated with `size_name` and `size_source_digest`. Deployments, readiness, smoke
results and benchmarks pin that resolved revision; editing a size does not change
running containers. Catalog rows retain the latest parent family; resolved sizes
remain in revision history and are visible on Models and Deployment.

GPU reservation per device is `max(mib_per_device, ceil(fraction * total_mib))`.
A typed utilization override also sets that fraction. Use the MiB floor for
weights, explicit KV, workspaces and a safety margin, including startup peaks.
Explicit KV sizing changes vLLM's actual allocation; this formula intentionally
remains conservative rather than claiming an exact footprint. Unspecified recipes
remain exclusive, and sharing must be permitted by the host's Fleet policy.
Docker RAM limits reserve host memory separately. On GB10 the GPU estimate must
fit inside that RAM reservation; unified memory is not counted twice.

Fleet reports host-owned `managed_capacity`: RAM budget/reservations and each
GPU's total, usable budget, reservations and exclusive owner. Central API admission
checks fresh capacity and durable desired placements before committing changes;
Fleet atomically checks local reservations again. Ready/pending/stopping workloads
hold resources, including after restart. The UI distinguishes measured available
memory from unreserved budgets. GPU reservations are estimates, not CUDA quotas.

Single-host deployment IDs may move only after the old host has positively
reported unload. Its durable local desire remains unloaded; new generations and
observations belong to the new host. Changing revisions also requires observed
unload. Distributed group moves still require a new placement.

## Physical GPU placement and measured memory

Each selected host can supply `gpus: [2, 3]` in the deployment-group request.
The controller persists these physical indices in that rank's placement, renders
`device=2,3` for Fleet and reserves those devices rather than the recipe defaults.
The selected count must match the recipe's explicit per-rank device count; duplicate,
missing, incompatible and out-of-range devices are rejected. Every rank can choose
different indices. Omission preserves existing placements and recipe selections.
Changing GPUs requires observed unload, just like changing the executable revision.

The Deployment page shows device selection, measured utilization/VRAM and unreserved
budgets per GPU. Pending central placements count before the next Fleet observation.
Models and Deployment display physical indices. NVIDIA visibility uses physical host
IDs; CUDA visibility remains local to the exposed container devices. Changing placement
does not edit the immutable recipe or its tensor-parallel degree. Shared memory settings
apply per selected device; host RAM still has a separate budget.

Smoke evidence may include a bounded `memory_profile`, pinned to revision, host,
generation and physical placement. It records sampled NVIDIA process GPU peaks,
kernel container RAM peaks, unified working-memory peaks, sampling interval/duration,
tested context/concurrency/image pixels and the explicit safety-margin rule. At least
two successful requests, no failures and measurements for every assigned device are
required. The source remains an operator measurement report, not an automatically
certified universal requirement. Recipes shows measured peaks separately from
reservation budgets and links each resolved size to its own evidence.

Fixed KV bytes disable vLLM's utilization-based profiling. A calibrated size can
explicitly declare `gpu_memory.fraction: 0` to reserve its measured MiB requirement
plus margin while retaining the engine utilization setting. Without an explicit
fraction override, the typed utilization setting still sets the reservation fraction.
Measurements apply to the recorded image, settings, GPU family and tested workload;
changes require validation again. Sampled peaks include startup and inference; a
budget adds a visible margin rather than treating idle usage as the requirement.

Explicit physical GPU selections are resolved to host-reported NVIDIA GPU UUIDs.
Fleet still reserves physical host indices, while CUDA_VISIBLE_DEVICES uses the
pinned UUIDs so privileged containers and differing CUDA enumeration orders select
the same hardware. Stop preserves those identities even if the host is offline.

Administrators can retire a single-host desired placement with
`DELETE /dashboard/api/management/deployments/{id}?expected_generation=N`.
The current generation must be positively observed unloaded. This removes only
the desired record; immutable recipe revisions and validation evidence remain.
Distributed groups cannot be partially removed. Use a fresh ID for a later
deployment; Fleet retains the retired ID's accepted generation.

## Host sampling and PCIe

Fleet exposes independently configurable local host/GPU/container collection
intervals, plus per-metric overrides and `off` via `FLEET_METRIC_INTERVALS`.
Host details include a sortable/filterable sampling table showing each metric's
effective interval and last observation. Disabled/stale readings remain unavailable
in history graphs. Host details also show GPU backend/read duration
and separate GPU/container sample timestamps. Hosts graph selectors include GPU
PCIe RX/TX totals; the detail view includes current/max generation/width and raw
replay, correctable error and recovery counters. Unsupported values remain
unavailable. RX enters the physical GPU, TX leaves it; charts scale NVML KB/s to
decimal MB/s. Rates describe the driver's short sampling window, not the stored
chart bucket. Totals require every device to provide the metric; a missing device
does not appear as a lower measured total. Recoveries include normal power
management, and an idle low-generation link is normal.

Local 100 ms collection does not change five-second mesh reporting or
fifteen-second SQL history collection. Fast intermediate observations are not
retained. See Fleet's `docs/telemetry.md` for settings and measurement costs.

Container names/images/state come from independent inventory collection. CPU/RAM/PIDs
are optional informational readings; readiness and placement use separate data.
Fleet uses bounded Docker Engine one-shot reads instead of the `docker stats` CLI.
Disabling all three container resource metrics leaves inventory intact and makes
zero Engine stats requests. Per-metric metadata survives Fleet, worker/controller
mesh serialization, SQL history and the dashboard API; legacy agents omit it.

Host details graph each physical GPU separately, selected by UUID and displayed
in index order; CPU/RAM/network remain host measurements. Individual GPU selectors
reuse the shared history charts and legends. The fleet overview keeps host-level
GPU averages and PCIe totals. GPU fan speed is available in the graph selector and
per-GPU details, with its own `gpu_fan` interval/off setting. Unsupported sensors
remain unavailable and legitimate zero readings stay zero. NVML reports intended
operating percentages rather than actual RPM; values above 100% are preserved.

### Filesystem and block-device observations

Fleet carries bounded optional `filesystems` and `block_devices` arrays through
mesh and stored host history; legacy snapshots without them remain valid. Hosts
show sortable/filterable tables for capacity, available vs reserved space, inode
usage, host mount access modes and whole-device I/O. Mount/device selectors share
the existing history viewer and time ranges; historical devices remain selectable.
The overview uses root filesystem capacity and leaf-device I/O totals, maximum
leaf busy percentage and IOPS-weighted latency. Logical layers can be selected
individually in host details without adding them to host totals. Unsupported,
initial/reset, stale/off values and idle latencies remain unavailable.

Fleet defaults `disk` to 30 seconds and `disk_io` to one second, independently of
CPU/GPU/container sampling. These counters use host mounts and kernel statistics;
no filesystem directory scans, Docker stats or Prometheus are involved. Mesh and
SQL history cadence remain unchanged.

## Client-facing model aliases

Infrastructure → Aliases (`#/aliases`) manages stable names independently of host
placement. The shared table sorts and filters aliases, primary/fallback profiles,
upstream model IDs and backends. Administrators can add, rename, retarget, reorder
fallbacks and delete; mutations use the existing origin/CSRF guard and SQL revision
compare-and-swap. Names cannot conflict with profiles or explicit configured routes.

Operational YAML aliases bootstrap SQL `model_aliases` once. Thereafter SQL is
authoritative, including an empty alias collection. Config generation/sync must
not re-import or resurrect old aliases. Backend/profile UUID references retain their
current configured remaps and per-provider defaults; no credentials are copied into
alias records or returned by the API. Removed profiles produce repairable errors.

Each inference request freezes its route, request-level primary profile and replay
cache revision before normalization/token budgeting/vision gating. Existing streams
and tool loops finish against that snapshot after an edit. Backend authorization,
admission and pre-first-chunk failover continue through the existing routing client.
Renamed/deleted names return 404 instead of falling through to a default backend,
even in passthrough mode. Key/traffic policy names are not rewritten automatically.
See [configuration ownership and remaining gaps](dashboard-configuration.md).
